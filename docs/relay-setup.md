# Установка на два сервера: relay и exit

## Когда это нужно

Обычной установки на один сервер достаточно, пока клиенты до него дотягиваются.
Если провайдер или мобильный оператор фильтрует сам адрес сервера, картина
выглядит так: ping проходит, TCP-соединение на 443 устанавливается, а
TLS-handshake не завершается никогда, причём одновременно перестают открываться
и панель, и все проксируемые сайты. На сервере в это время всё исправно.
Проверяется это парой измерений с двух сторон, см. «Диагностика зависаний» в
[operations.md](operations.md): в `sudo adguardhome-doh-diag` растёт
`no_clienthello`, а `tools/client-probe.sh` показывает `rc=28` при ненулевом
`connect` и нулевом `tls`.

Никакая настройка сервера не заставит потерянный в пути пакет дойти. Установка
разносится на два хоста:

- **relay** стоит там, куда клиенты дотягиваются без потерь;
- **exit** стоит там, откуда доступны нужные сервисы.

## Схема

```text
iPhone ──DoH──► relay (RU)  ──TLS как есть──►  exit (NL)  ──►  chatgpt.com
                 │  отдаёт свой IP для               маршрутизирует
                 │  доменов каталога                 по тому же SNI
                 └─ AdGuard Home, health-gate, профиль
```

TLS нигде не расшифровывается: relay пересылает байты клиентского соединения
как есть, exit разбирает у них только SNI, клиент получает настоящий сертификат
сайта. Задержка растёт на один хоп.

На relay живут DoH, AdGuard Home, health-gate и Apple-профиль. Exit это обычная
установка без единого изменения: он и так маршрутизирует TLS любого клиента по
SNI. Health-gate на relay проверяет цепочку целиком, потому что его пробы идут
тем же путём, что и клиенты.

## Что понадобится

- Два сервера с Ubuntu 24.04 или новее, root или sudo без пароля.
- Отдельное DNS-имя с A-записью для каждого: например `dns-exit.example.com`
  на IP exit-хоста и `doh.example.com` на IP relay-хоста. Установщик сверяет
  A-запись с указанным `--public-ip` и без совпадения не начнёт работу.
- На обоих хостах открыты TCP 80 и TCP 443. Порт 80 нужен постоянно: через него
  продлевается сертификат. Порт 53 наружу не нужен.
- Один и тот же набор сервисов на обоих хостах. Exit отбрасывает соединения с
  незнакомым SNI, поэтому его набор должен совпадать с набором relay или быть
  шире.

## Шаг 1. Exit-сервер

Обычная установка, флаг `--relay` здесь не используется.

```bash
curl --fail --silent --show-error --location https://raw.githubusercontent.com/evgenykhripach/AdguardHomeDoH/main/bootstrap.sh | sudo bash -s -- --domain dns-exit.example.com --public-ip 203.0.113.10 --email admin@example.com --services chatgpt,claude,gemini --yes
```

Без флагов та же команда откроет интерактивный мастер с выбором сервисов по
категориям. Запишите итоговый список сервисов, он понадобится для relay.

Проверьте, что exit поднялся:

```bash
sudo adguardhome-doh-diag --minutes 5
```

Дождитесь, пока health-gate наберёт три успешных цикла: в журнале
`healthy_services` станет равно числу выбранных сервисов.

```bash
sudo journalctl -u adguardhome-doh-health.service --since -10min --no-pager -o cat | tail -3
```

Если exit-хостом вы пользуетесь только как выходом и его собственный DoH не
нужен, порт 443 на нём можно ограничить адресом relay. Порт 80 оставьте
открытым для всех, иначе перестанет продлеваться сертификат.

## Шаг 2. Relay-сервер

Дальше два варианта в зависимости от того, свободны ли на relay порты 80 и 443.

### Вариант A: чистый хост

```bash
curl --fail --silent --show-error --location https://raw.githubusercontent.com/evgenykhripach/AdguardHomeDoH/main/bootstrap.sh | sudo bash -s -- --domain doh.example.com --public-ip 198.51.100.20 --email admin@example.com --relay 203.0.113.10 --services chatgpt,claude,gemini --yes
```

`--relay` принимает IPv4 exit-хоста. Он должен отличаться от собственного адреса
relay, иначе каждое проксируемое соединение замкнётся на себя, и установщик это
отклонит. Список `--services` тот же, что на exit.

### Вариант B: перед существующим сайтом

Если на relay уже работает nginx с сайтом на 443, установщик встанет перед ним:
443 займёт stream-слой, а сайту вернёт его собственный SNI на внутреннем порту.
Сайт будет видеть всех клиентов как `127.0.0.1`, потому что TLS не
расшифровывается и PROXY protocol не используется.

**1. Установите stream-модуль.** Единственный перезапуск nginx во всей
процедуре, около секунды простоя. Если модуль уже стоит, перезапуск не нужен.

```bash
sudo apt-get install -y --no-install-recommends libnginx-mod-stream apache2-utils && ls /etc/nginx/modules-enabled/ && sudo nginx -t
```

Если в списке не появился `50-mod-stream.conf`, перезапустите nginx:

```bash
sudo systemctl restart nginx
```

**2. Переведите сайт на внутренний порт, не перезагружая nginx.** Конфигурация
на диске меняется, работающий процесс продолжает держать 443 со старой. Ниже
пример для сайта, выпущенного certbot; подставьте имя своего файла и сначала
сделайте копию.

```bash
sudo cp -a /etc/nginx/sites-available/ВАШ_САЙТ /root/ВАШ_САЙТ.bak && sudo sed -i -e '/listen \[::\]:443 ssl/d' -e 's|^\([[:space:]]*\)listen 443 ssl;.*|\1listen 127.0.0.1:9443 ssl;|' /etc/nginx/sites-available/ВАШ_САЙТ && sudo grep -n listen /etc/nginx/sites-available/ВАШ_САЙТ && sudo nginx -t
```

Убедитесь в выводе, что вместо `listen 443 ssl;` появилась строка
`listen 127.0.0.1:9443 ssl;`, строки `listen [::]:443` больше нет, а блок на
порту 80 не тронут: через него сайт продлевает свой сертификат. `nginx -t`
должен пройти успешно.

**3. Установите relay перед сайтом.**

```bash
curl --fail --silent --show-error --location https://raw.githubusercontent.com/evgenykhripach/AdguardHomeDoH/main/bootstrap.sh | sudo bash -s -- --domain doh.example.com --public-ip 198.51.100.20 --email admin@example.com --relay 203.0.113.10 --local-site app.example.com=127.0.0.1:9443 --local-site '*=127.0.0.1:9443' --services chatgpt,claude,gemini --yes
```

`--local-site HOST=IPV4:PORT` повторяется для каждого имени сайта.
`--local-site '*=IPV4:PORT'` задаёт цель для соединений без SNI и с незнакомым
именем: без него перестанет работать вход по IP-адресу, который раньше отдавал
сайт. Порт 443 в качестве цели запрещён, его занимает stream-слой. Установщик
проверит общую конфигурацию и применит оба изменения одним graceful reload,
затем выпустит свой сертификат через собственный блок на порту 80.

## Шаг 3. Клиент

Установщик напечатает адрес панели, пароль, DoH-ссылку и ссылку на
`.mobileconfig`. Их же в любой момент показывает пункт 1 меню
`sudo adguardhome-doh`.

На iPhone откройте ссылку на профиль **с relay-хоста** в Safari, затем
Настройки → «Профиль загружен» → «Установить». Профиль ограничен доменами
каталога через `SupplementalMatchDomains`, поэтому остальной DNS устройства
остаётся у текущей сети, а на iOS 26 и новее ключ `AllowFailover` разрешает
откат на системный резолвер, если сервер недоступен.

Если раньше стоял профиль другого хоста, удалите его: он продолжит ходить на
старый адрес напрямую. Профили разных доменов имеют разные идентификаторы и
друг друга не заменяют.

## Проверка

На relay-хосте:

```bash
sudo adguardhome-doh-diag --minutes 10
```

Ожидается `connections` больше нуля, `upstream_failures=0`, а в строке `health`
значения `doh_fail=0` и `global_failure=0`.

Проксируемый домен должен резолвиться в адрес relay с TTL 300:

```bash
dig @127.0.0.1 chatgpt.com A +noall +answer
```

Вся цепочка целиком, ответ приходит с реального сайта через exit:

```bash
curl -s -o /dev/null -w 'http=%{http_code} remote=%{remote_ip}\n' --max-time 15 --resolve chatgpt.com:443:198.51.100.20 https://chatgpt.com/
```

Код 403 от Cloudflare здесь нормален: так отвечают голому curl без браузера.
Важно, что `remote` равен адресу relay и ответ вообще пришёл.

Для варианта B дополнительно проверьте сайт по имени и по IP:

```bash
curl -s -o /dev/null -w 'по имени: %{http_code}\n' https://app.example.com/ && curl -sk -o /dev/null -w 'по IP: %{http_code}\n' https://198.51.100.20/
```

## Обслуживание

**Обновления.** На каждом хосте отдельно: `sudo adguardhome-doh`, пункт 4.
Значения `--relay` и `--local-site` хранятся в `install.json` и переносятся
автоматически, задавать их заново не нужно.

**Смена набора сервисов.** Сначала на exit, потом на relay, через пункт 2 меню.
Порядок важен: пока сервис включён на relay, но выключен на exit, exit будет
отбрасывать его SNI. Обратный порядок безопасен, лишний сервис на exit просто
не используется.

**Если exit недоступен.** Пробы relay падают все разом, health-gate распознаёт
это как локальный сбой, сохраняет прежнее состояние и пишет `global_failure=1`,
чтобы не отправить клиентов на реальные адреса. Проксируемые сайты в это время
не открываются, остальной интернет на устройстве работает, потому что профиль
ограничен доменами каталога. Exit обязателен для работы связки.

## Откат

Полный откат последнего изменения на любом хосте: `sudo adguardhome-doh`,
пункт 5.

Для варианта B, чтобы вернуть сайт на 443 и убрать relay целиком:

```bash
sudo cp -a /root/ВАШ_САЙТ.bak /etc/nginx/sites-available/ВАШ_САЙТ && sudo rm -f /etc/nginx/stream.d/adguardhome-doh.conf /etc/nginx/sites-enabled/adguardhome-doh && sudo nginx -t && sudo systemctl reload nginx
```

После этого сайт снова слушает 443 напрямую, а stream-слой и DoH-эндпоинт
исчезают.
